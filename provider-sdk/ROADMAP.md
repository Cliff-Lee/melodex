# Provider SDK / Ecosystem Roadmap

This roadmap separates **what exists now** from **what is still a design target**.

For the most precise current status, see [Status, stability and trust](../docs/developers/00_STATUS_AND_STABILITY.md).

## Current foundation

Implemented in the public Melodex repository:

- MPP provider manifest/schema;
- JSON-RPC subprocess provider runtime;
- `.mdxprovider` installer and packaging;
- Provider Manager in desktop Core;
- Local Files and source-neutral resolver/playback path;
- `melodex-provider init/validate/doctor/pack`;
- web/session helpers and vendored dependencies;
- experimental v0.1 capability contracts;
- Capability Broker and `.mdxplugin` runtime;
- `melodex-extension init/validate/doctor/pack`;
- Plugin Directory + canonical registry;
- SHA-256/size verification for registry installs;
- `melodex-registry` validation/package-integrity tooling;
- legal/open reference integrations;
- installation provenance/update-awareness work in the desktop app.

## 0.5 — developer experience + truth layer

Current campaign:

- one obvious 5-minute developer path;
- consistent provider/extension scaffolds;
- source-policy file generated by default;
- automated internal documentation-link checks;
- explicit implemented/preview/experimental/planned labels;
- accurate current security/permission language;
- installation provenance (manual vs registry);
- user-visible update availability.

## 0.6 — trust enforcement + diagnostics

Planned:

- provider/extension health dashboard;
- structured redacted diagnostic export;
- clearer crash/restart state;
- stronger child-process environment isolation;
- explicit credential/configuration broker for authenticated third-party providers;
- richer permission-policy enforcement where technically possible;
- registry update/change history in UI.

## 0.7 — publisher identity

Planned:

- signed package format;
- verified-publisher keyring/trust store;
- signature verification independent of registry transport;
- key rotation/revocation design;
- reproducible packaging guidance.

## 0.8 — conformance

Planned:

- protocol conformance runner beyond current `doctor` smoke tests;
- compatibility fixtures across SDK releases;
- provider/capability conformance badges based on reproducible tests.

## 1.0 — compatibility commitment

Only after real ecosystem use:

- freeze required MPP method names/fields;
- explicit deprecation policy;
- compatibility test matrix;
- stable capability-negotiation rules;
- documented migration window for breaking changes.

Do not infer a stable 1.0 promise merely from today's `protocol_version: "1.0"` preview identifier.
