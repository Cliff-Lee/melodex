# Melodex v0.7.9

## Elastic Library Engine

v0.7.9 is a large-library performance and reliability release.

The main goal was simple:

> Melodex should scale from ordinary personal collections to extremely large libraries without freezing the interface or forcing smaller libraries to pay for million-track complexity.

### Faster large-library scanning

The local-library scanner now uses a bounded streaming pipeline instead of accumulating discovery work without limit.

Changes include:

- streaming discovery rather than a separate whole-library discovery buffer;
- a bounded 256-row producer/consumer queue with backpressure;
- bounded SQLite write/delete batches;
- production traversal using `os.scandir()` and `DirEntry.stat()`;
- unchanged-directory bulk reuse after filename + size + mtime verification;
- adaptive metadata concurrency for fast local storage versus higher-latency/NAS-style storage.

At 100,000 synthetic tracks on GitHub-hosted runners, the same qualification workload improved from approximately:

| Scenario | Before Campaign 10 | v0.7.9 |
| --- | ---: | ---: |
| Cold scan | ~38.0 s | ~29.7 s |
| Unchanged rescan | ~32.7 s | ~13.1 s |
| Tiny delta | ~33.9 s | ~12.9 s |
| Warm/delta traced Python peak | ~114 MiB | ~47 MiB |

Runner timings vary; these figures are useful as directional engineering measurements rather than guaranteed device benchmarks.

### Incremental rescans do less work

Melodex already used size + modification-time fingerprints before this release. v0.7.9 builds a more scalable pipeline around them.

An unchanged rescan now:

- reopens no audio metadata;
- rewrites no track rows;
- can preserve a verified unchanged directory as a unit rather than rematerialising all of its cached track dictionaries.

A tiny delta scales with the changed portion rather than the full library. In the 1,000,000-track qualification, a synthetic change of 50 modified + 50 added + 10 deleted files produced exactly:

- 100 metadata reads;
- 100 track writes;
- 10 track deletes.

### Safer cancellation and restart

Library scanning now has durable scan generations and checkpointed staging.

Successfully read changed-file metadata is staged separately from the live library. If a scan is cancelled or the worker process stops:

- no partial catalog is published;
- incomplete/offline NAS roots are not interpreted as mass deletion;
- compatible staged metadata can be reused on restart when the current size + mtime fingerprint still matches.

### Lower duplicate-memory pressure

The isolated production scan path no longer keeps several parallel whole-library track representations at once.

During scanning it retains the persistence representation, commits it atomically, releases it, then hydrates the completed catalog from SQLite.

Unchanged-directory reuse further reduces warm/delta memory pressure.

### Million-track qualification

v0.7.9 adds repeatable release-scale qualification at:

- 100,000 tracks;
- 250,000 tracks;
- 500,000 tracks;
- 1,000,000 tracks.

The first full 250k / 500k / 1M matrix passed all permanent gates.

At 1,000,000 synthetic tracks the qualification verified:

- discovery queue remained bounded at 256;
- metadata work remained bounded at 8 in flight;
- unchanged rescan performed zero metadata reads;
- unchanged rescan rewrote zero track rows;
- delta work followed only the changed/new files;
- cancellation published no partial catalog;
- 256 staged rows were reused successfully after restart;
- memory remained within the linear scale gate.

A clean 1M cold-path run without `tracemalloc` measured approximately:

- 74.6 s scan;
- 38.7 s SQLite persistence;
- 1.22 GiB RSS after scan;
- 1.72 GiB peak after persistence;
- ~629 MiB SQLite index.

These are synthetic virtual-filesystem qualification numbers, not a claim that every physical disk, SMB share or NAS will achieve the same wall time. Real storage latency remains highly device- and network-dependent.

### Permanent regression gates

The test suite now protects the scaling architecture with checks for:

- bounded discovery queue;
- bounded metadata concurrency;
- zero metadata reads on unchanged rescans;
- zero DB rewrites on unchanged rescans;
- delta work proportional to changed/new files;
- cancellation and restart correctness;
- linear Python-memory scaling;
- release-scale 100k–1M qualification.

### Compatibility and safety

This release deliberately avoids unsafe shortcuts such as treating an unchanged parent-directory timestamp as proof that every descendant file is unchanged.

Directory reuse is only accepted after verifying sorted audio filename + size + modification-time fingerprints.

Your music files are still not copied, moved or rewritten by library scanning.

## Validation

v0.7.9 has been validated with:

- Python 3.11 and 3.12 test suites;
- Fluid Melodex responsiveness gates;
- 12.7k mixed-workload soak;
- 12.7k elastic-library qualification;
- 100k performance qualification;
- 250k / 500k / 1M release-scale qualification;
- cancellation/restart and incomplete-root tests;
- desktop package builds;
- Linux package builds and smoke checks.

macOS, Windows, Linux and Android distribution artifacts are built by the standard release workflow.
