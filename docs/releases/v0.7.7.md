# Melodex v0.7.7

## A much more fluid Melodex

This release is primarily about how Melodex behaves under load: large libraries should no longer make the interface feel stuck, navigation acknowledges immediately, and expensive work is bounded, cancellable and kept away from the UI thread wherever possible.

## Large-library responsiveness

- Adds reproducible 1k / 12.7k / 50k / 100k synthetic library profiles and sustained 12.7k soak tests.
- Virtualizes the large Tracks view so only the visible window is rendered first instead of materialising the whole collection.
- In the campaign benchmark, the 12,700-track Tracks view fell from roughly **705 ms to about 37 ms** for the measured render path.
- Artwork work is viewport-first: visible cards first, nearby cards next, distant artwork last.
- Adds a bounded background scheduler with priorities, lane limits and a reserved foreground slot so bulk work cannot starve interactive work.
- Replaces stale queued work when navigation/search state changes and drops results that no longer belong to the current UI state.
- Keeps slow work separate from interaction acknowledgement: background tasks may take time, but the interface should not freeze while they run.

## Faster startup

- Adds detailed startup phase instrumentation for fresh, warm, profile-cold and large cached-library launches.
- Heavy pages such as My Music, Now Playing, Album Wall and Music Map now start as lightweight shells and build on first navigation.
- Keeps cached local-library metadata on disk until a feature actually needs the full catalogue.
- Home reads a cheap indexed track count instead of JSON-decoding the entire cached library.
- Skips redundant SQLite schema/root writes on unchanged warm launches.
- Defers plugin registry, OS keyring and external provider secret configuration until they are actually needed.
- Keeps NumPy, Requests, metadata enrichment, Music Knowledge, LLM and Journey-related feature graphs off the cold Home path where possible.
- The measured 12.7k cached-library startup premium fell from about **82.6 ms to about 6.4 ms** in the controlled CI comparison.

## Packaged-app startup is now tested too

- Measures startup of the actual macOS ARM/Intel, Windows, Linux `.deb` and AppImage builds.
- Records process-launch to first Qt event-loop turn as well as Melodex's internal startup timeline, exposing packaging/bootloader overhead that source-mode tests cannot see.
- P9e caught a real macOS Intel issue where automatic startup of the local AI/control bridge could block launch for about **35 seconds**.
- The local control bridge now starts on background work, so a slow networking stack can delay bridge availability without delaying Home or local playback.
- After that fix, the Intel packaged startup returned to the normal multi-second range instead of ~36–37 seconds.

## Responsiveness contracts and regression gates

Melodex now has explicit CI-visible responsiveness expectations:

- interaction acknowledgement p95 under 100 ms, with under 50 ms preferred;
- navigation shell under 100 ms;
- 250 ms event-loop gaps treated as CI-budget violations;
- 500 ms gaps treated as serious defects;
- 1 second gaps treated as release blockers.

The release gates now include large-library baselines, sustained mixed-workload soak testing, startup probes, packaged-startup probes, and cross-platform package smoke checks.

## What this means for listeners

The main benefit is less waiting on Melodex itself. Opening pages, browsing a large collection, starting the app and moving between views should feel more immediate even when indexing, artwork, provider or analysis work is still happening behind the scenes.

This is still a public beta, so large and unusual libraries remain especially useful for testing.
